# 13 项边界隐患判定细则

---

## 1. 32 位毫秒 tick 回绕

**现象**
- `uint32_t` 毫秒计数约 49.7 天回绕一次。
- `int32_t` 毫秒计数约 24.85 天回绕一次。
- 回绕后，超时、周期任务、告警抑制、上报节流可能**永不触发或立刻误触发**。

**设计阶段动作**
- 明确本产品计数器/定时器的位宽和驱动频率，算出实际回绕周期（`回绕周期 = 计数器容量 ÷ 计数频率`）。
- 任何"安全窗口 / 容错窗口"类参数，本质上是在和回绕周期"抢空间"——必须按 `总回绕周期 − 容错窗口 = 实际可用等待窗口` 核算，并与业务里最长的定时器需求逐一比对，不能只看回绕周期本身够不够长。
- 长通电设备（网关、常电路由/传感）方案里必须显式写明"已考虑回绕"，而不是默认"用不到这么久"。

**检查/评审动作**
- 要求方案提交方给出**"回绕周期计算表"**（主频 → 计数位宽 → 回绕秒数 → 可用窗口）。
- 检查所有运行时长可能超过回绕周期 `1/10` 的定时器/超时逻辑，是否用了无符号/环形比较而非直接大小比较。
- 对任何"沿用其他产品/供应商推荐值"的底层参数，要求提供该参数在本产品场景下的重新推导依据，不接受"经验值直接复用，没算过"。

**验证方法**：把 tick / 时间源人为拨到回绕点附近，观察超时、周期任务、抑制窗口是否按预期触发。

**快速核算（常用值）**

| 计数位宽 | 计数频率 | 回绕周期 |
|---|---|---|
| 32 位 | 1 kHz（1 ms） | 约 49.7 天 |
| 32 位 | 1 MHz（1 µs） | 约 71.6 分钟 |
| 32 位 | 4 MHz | 约 1074 秒 |
| 32 位 | 16 MHz | 约 268 秒 |
| 16 位 | 1 kHz（1 ms） | 约 65.5 秒 |

## 2. 时间差计算写法错误

**现象**：`now > last + timeout`、有符号减法、有/无符号混用，在回绕点行为错误。

**设计阶段动作**
- 统一用**无符号时间 + 无符号间隔**做差值判断，或直接用系统提供的 elapsed / uptime API，不要自己拼减法比大小。
- 涉及跨模块共享的时间变量，要在设计文档里注明类型（有符号/无符号）和单位，避免后续维护者按"想当然"去改。

**检查/评审动作**
- 代码走查时专门检索 `now - last`、`now > last + timeout` 这类模式，逐一核对类型与运算方式。
- 做**"拨表测试"**：把 tick/时间源人为拨到回绕点附近，观察超时、周期任务、抑制窗口是否按预期触发。

**判定要点**：正确形态是 `(uint32_t)(now - last) >= timeout`；`now > last + timeout` 在 `now` 回绕后必然误判。

## 3. 「类千年虫」绝对时间耗尽

**现象**
- 有符号 32 位 Unix 秒 → **2038-01-19** 溢出。
- 无符号 32 位秒、16 位日计数、自定义纪元、RTC 位宽不足，也会在某个日期突然坏掉。

**设计阶段动作**
- 明确产品设计生命周期（如 10 年 / 15 年），核算系统时间字段（`time_t` 位宽）、协议时间字段、RTC 位宽是否能覆盖到生命周期结束，而不是默认"现在够用就行"。
- 底层工具链 / OS 默认的时间类型位宽要**书面确认**，不要假设"新芯片肯定是 64 位"。

**检查/评审动作**
- 评审时要求提供**"时间字段耗尽日期计算表"**，逐字段列出耗尽年份。
- 对不满足产品生命周期要求的时间字段，必须明确升级方案（如切换 64 位 `time_t`）或业务规避方案，**缺一不可**。

**验证方法**：确认生命周期内绝对时间与协议时间字段不耗尽（含 2038）。

---

## 4. 非法 / 未同步时间参与业务

**现象**：时间为 0、未对时、掉电乱值、明显未来时间，若直接用于告警、存储索引、有效期、上下行判断，会引发连锁异常。

**设计阶段动作**
- 设计对时完成前的默认状态和"未同步"标志位，所有依赖时间的业务逻辑要有**明确的降级路径**（而不是当正常时间用）。

**检查/评审动作**
- 走查所有使用系统时间的模块，确认是否有"时间是否已同步"的前置判断。
- 专项测试：上电未对时、对时失败、时间被恶意/异常设置为极端值时的业务表现。

---

## 5. 定长累计计数溢出

**现象**：能量、电量、脉冲、运行时长等 `uint16/32` 累加器溢出后变小或跳变。

**设计阶段动作**
- 预估产品生命周期内的最大累计值，据此选择足够位宽，或明确定义溢出后的业务语义（**保持 / 回绕 / 扩位存储三选一，不能没定义**）。

**检查/评审动作**
- 评审要求提供**"最大累计值估算表"**（按预期使用强度 × 生命周期年限计算）。
- 对累计类字段做加速老化/仿真测试，验证溢出后的真实表现是否符合设计预期，而不是"跑不到那么久就不管"。

---

## 6. 序列号 / 报文序号回绕

**现象**：用「更大即更新」判新旧时，序号一回绕会把旧包当新包（或丢弃新包）。

**设计阶段动作**
- 协议设计阶段就要明确序号位宽和回绕窗口的比较规则（**环形比较**），不能简单写"数值大的就是新的"。

**检查/评审动作**
- 走查本地状态机里所有"新旧包判断"逻辑是否使用了环形比较规则。
- 构造临界序号（回绕前后各几个值）做专项测试。

**判定要点**：`(int32_t)(new_seq - old_seq) > 0` 或 `(uint16_t)(new - old) < 窗口/2` 是环形比较；`new_seq > old_seq` 不是。

---

## 7. 协议长度字段导致缓冲越界

**现象**：长度为 0、小于头长、大于接收缓冲时，若未先校验再拷贝，可直接 HardFault / 内存破坏。

**设计阶段动作**
- 所有来自对端的长度字段，设计时就要规定"**先与本地缓冲容量取小并校验合法性，再决定是否拷贝/解析**"，这是接口设计的强制约束项，不是编码细节。

**检查/评审动作**
- 走查所有协议解析入口，确认**长度校验发生在拷贝/内存操作之前**。
- 做模糊测试（fuzzing）：构造超大、超小、零长度的异常包，验证解析鲁棒性。

**判定要点**：`memcpy(dst, src, hdr.len)` 必须先有 `if (hdr.len == 0 || hdr.len > sizeof(dst) || hdr.len < HDR_LEN) return ERR;`。

---

## 8. 环形队列满 / 空判错

**现象**：满时覆盖未读数据，或空读当有效数据，会导致事件丢失、状态错乱、偶发逻辑诡异。

**设计阶段动作**
- 选定**单一的**满/空判定策略（如多留一格法或独立计数法），并明确队列满时的丢弃/覆盖策略，写进设计文档，不要留给实现者临场决定。

**检查/评审动作**
- 走查判满判空逻辑是否**全局统一**（同一产品不同模块用不同策略是常见坑）。
- 高负载压测，验证队列满时的实际表现是否与设计预期一致。

**判定要点**：`head == tail` 单独无法区分满与空——要么多留一格（`(head+1)%size == tail` 为满），要么独立 `count` 变量并显式记录"满"标志。

---

## 9. 有符号 / 无符号混用与比较翻转

**现象**：长度、差值、剩余空间等参与比较时类型不一致，结果可能完全反转。

**设计阶段动作**
- 接口和变量类型定义阶段就统一有符号/无符号使用规范，接近类型上限的运算提前评估溢出风险。

**检查/评审动作**
- 走查所有涉及长度/差值/剩余空间比较的代码，检查**两侧类型是否一致**。
- 针对类型边界值（0、最大值、最大值 − 1）做专项测试。

**典型陷阱**：`int len = sizeof(buf);`（`sizeof` 是 `size_t`）；`if (a - b > 0)` 在无符号下恒真；`uint16_t remain = cap - used;` 当 `used > cap` 时翻转成巨大值。

---

## 10. 数组与拷贝越界（含 off-by-one）

**现象**：`index == capacity`、`len == 0` 未特判、`memcpy` 长度多 1，都是经典死机源。

**设计阶段动作**
- 循环与拷贝统一用"**有效长度**"约束，空缓冲走单独路径设计，不要指望循环条件"顺便"处理边界。

**检查/评审动作**
- 走查所有 `memcpy` / 循环的边界条件写法。
- 专项测试 `index == capacity`、`len == 0` 等边界输入。

**典型陷阱**：`for (i = 0; i <= len; i++)`、`arr[len]`、`strncpy(dst, src, sizeof(src))`、`memcpy(dst, src, len + 1)`。

---

## 11. 下行配置量程与本地类型装不下

**现象**：云端 / App 下发的周期、阈值、时间窗等，协议允许但本地 `uint8/16` 或业务量程装不下。

**设计阶段动作**
- 设计下行参数接收接口时，明确本地类型的最大量程，并规划**二次校验 / 裁剪**逻辑，不能假设"云端不会发出格的值"。

**检查/评审动作**
- 评审下行参数协议定义与本地类型定义是否匹配，**逐字段核对量程**。
- 构造超范围下行配置（如周期 = 0、阈值超大）做健壮性测试。

---

## 12. 上电 / 复位 / OTA 后的初值当合法数据

**现象**：未初始化内存、NVS 损坏、版本升级后旧字段语义变化，被当成合法时间、计数或配置。

**设计阶段动作**
- 设计关键字段（时间、配置、计数）的**默认安全值**，以及生命周期切换（上电/复位/OTA）后的**合法性校验流程**。

**检查/评审动作**
- 走查上电/OTA 后关键字段是否有合法性校验或回默认值逻辑。
- 专项测试：NVS 损坏、首次上电、OTA 后首轮行为。

**判定要点**：配置/持久化字段读出后应校验 magic + CRC + version，任一项不合法即回默认值。

---

## 13. 跨产品复用的底层 / SDK 参数未重新评估

**现象**：供应商 / 前项目给的调优参数（尤其是涉及硬件时钟周期、计数位宽相关的**容错窗口类参数**），换芯片主频、换定时器组合后可能完全不适用——这类参数通常被当成"调优参数"而非"边界参数"，容易在方案评审时被忽略。

**设计阶段动作**
- 任何"从别的产品/供应商建议直接沿用"的底层参数，必须结合本产品实际的硬件主频、定时器组合**重新推导边界**，形成参数选型依据并归档，不能凭经验直接复用。

**检查/评审动作**
- 评审时要求列出**所有"非 SDK 默认值"的底层参数清单及修改理由**。
- 对每一个非默认参数，索要推导依据和验证记录；缺失依据的按风险项处理，纳入技术维度风险复核（NUDD 评分 / 系统风险专项）。

**验证方法**：对所有"沿用其他产品/供应商建议"的底层参数，做**多定时器并发 / 特定时序**的专项压力测试（常规功能测试很难覆盖这类偶发场景）。

## 案例参考：定时器容错窗口参数复用导致周期任务调度异常

> 以下为**示意案例**：数值为便于演算的假想值，不对应任何具体产品，仅用于说明核算方法。

**现象**：设备运行若干时间后，某个周期性业务不再执行，时间/日期显示仍正常，重新上电后问题消失；常规功能测试无异常，属偶发、定位耗时较长的一类。

**根因（对应条目 1 + 13）**
- 设备采用 32 位滴答计数器，计数频率 4 MHz，约每 **1074 秒**回绕一次；
- 固件中的"定时器过期容错窗口"参数被设为 **900 秒**——该值沿用上一代产品，未结合本产品的定时器组合重新评估；
- 1074 秒的回绕周期里，900 秒被容错窗口占用，只剩约 **174 秒**可用于设置其他定时器；
- 项目中存在一个**周期 300 秒**的定时器，`300 秒 > 174 秒`的可用窗口，导致系统无法正确判断该定时器状态，调度异常，进而影响了与之共享定时器资源的采集任务。

**修复**：容错窗口参数恢复为 SDK 默认值（数秒级），问题不再复现；后续经过代码走查、回归测试、周期任务压力测试、多定时器并发测试及长期监测验证。

**这个案例说明的设计/检查动作**
- 设计阶段：任何容错窗口类参数，必须按"回绕周期 − 容错窗口 = 可用窗口"核算，并与产品实际最长定时器需求比对（对应条目 1）；沿用其他产品的底层参数前，必须重新评估是否适配本产品的硬件与定时器组合（对应条目 13）。
- 检查阶段：评审时应要求列出该类参数的推导依据；测试阶段应针对"多定时器并发 / 特定时序"做专项压力测试，而非仅做常规功能测试（低概率偶发问题在常规测试下很容易被漏测）。

## 现象 → 优先怀疑（现场定位用）

| 现象特征 | 优先查 |
|---|---|
| 跑几周到一个多月后才出 | 1、2（ms 回绕与时间差） |
| 某一天之后时间大面积错乱 | 3、4（纪元耗尽 / 未同步时间） |
| 累计值突然变小或跳变 | 5（累计溢出） |
| 重传 / 久跑后状态新旧颠倒 | 6（序列号回绕） |
| 异常包、大包后复位 | 7、10（长度与拷贝越界） |
| 忙时丢事件或逻辑乱跳 | 8（队列满空） |
| 仅某次配置 / 升级后出现 | 11、12（下行量程 / 初值） |
| 特定定时器组合 / 特定时序下偶发、常规测试难复现 | 1、13（回绕容错窗口 + 参数跨产品复用未评估） |

---

## 建议验证（少而关键）

- 把 tick 拨到回绕点附近，看超时、周期、抑制窗口。
- 确认生命周期内绝对时间与协议时间字段不耗尽（含 2038）。
- 加速或仿真累计计数、序列号回绕后的业务表现。
- 对伪造超大/超小长度包做解析鲁棒性验证。
- 非法下行配置、上电未对时、OTA 后首轮行为抽测。
- 对所有"沿用其他产品/供应商建议"的底层参数，做多定时器并发 / 特定时序的专项压力测试（常规功能测试很难覆盖这类偶发场景）。
